# Как инженеры Авито проверяют работы — чек-лист

Источник: github.com/avito-tech/tech-internship (коммит 05c1883 от 03.09.2026), разделы «Solution and advice» к заданиям Backend (весна 2024, осень 2024, зима 2025, весна 2025) и Frontend (весна 2024, осень 2024, весна 2025, зима 2025), а также задания 2026 года. Это то, что разработчики Авито чаще всего отмечали в работах кандидатов. Пересказ, сгруппированный для ревью.

## Запуск и README (первое, что делает проверяющий)

- [ ] Проект запускается **с нуля одной командой** (`docker compose up --build`), без ручных правок; все переменные окружения имеют **значения по умолчанию** или описаны в `.env.example`.
- [ ] В compose есть healthcheck и `depends_on`; миграции применяются предсказуемо (entrypoint или отдельный шаг).
- [ ] Версия Go в `go.mod` совпадает с образом в Dockerfile; Dockerfile multi-stage (бэк и фронт).
- [ ] Ответы соответствуют контракту (OpenAPI): коды, `Content-Type`, формат. URL и маршруты из ТЗ не переименованы.
- [ ] README: описание, запуск, стек, архитектура (C4 уровня 2–3), схема БД, особенности реализации, **принятые решения и компромиссы**, как запустить тесты, покрытие. Markdown, кратко и конкретно.
- [ ] Проверено не только в коде, но и **в браузере**: каждая заявленная функция реально работает.
- [ ] Чистая история коммитов: одна подзадача — один коммит, понятные сообщения.

## Go

- [ ] Слои: handler — только парсинг, валидация входа и маппинг ошибок; бизнес-логика — в service/usecase; репозиторий — только доступ к данным. Handlers разложены по доменам, не один `handlers.go`.
- [ ] Интерфейсы объявлены **на стороне потребителя** и узкие (по доменам, не «толстый» Repository); зависимость от интерфейса, а не от реализации.
- [ ] Валидация входных данных на входе; бизнес-правила (допустимые значения, статусы) — в приложении, а не CHECK-ограничениями в БД; в БД — целостность (NOT NULL, FK).
- [ ] **Проверка прав на сущность** (пользователь авторизован, но это не его заявка) — дополнительным условием в запросе или отдельной проверкой.
- [ ] Ошибки оборачиваются (`fmt.Errorf("...: %w", err)`), сравниваются через `errors.Is/As`, а не `==`/`strings.Contains`; пользователь **не видит** внутренние ошибки БД — маппинг на транспортном уровне.
- [ ] Транзакции — только там, где несколько изменений должны быть атомарными; решение — на уровне бизнес-логики (transaction manager, например avito-tech/go-transaction-manager); для гонок — блокировки, уровень изоляции или атомарный запрос с CTE.
- [ ] SQL безопасен: параметры, а не конкатенация; для динамических запросов — билдер (squirrel).
- [ ] Справочники (статусы, типы) — нормализованы в таблицы с id, а не строки/ENUM; индексы под фильтры, FK и сортировку/пагинацию (проверять `EXPLAIN ANALYZE`, не плодить лишние).
- [ ] Миграции отдельными файлами (`0001_...sql`) через golang-migrate, а не один `init.sql`.
- [ ] Graceful shutdown (сигналы, `srv.Shutdown(ctx)` с таймаутом); контекст пробрасывается везде.
- [ ] Конфигурация и секреты — из окружения; `.env` в `.gitignore`, в репозитории только `.env.example`; пароли — bcrypt.
- [ ] JWT/токен — в `Authorization: Bearer <token>`.
- [ ] Логирование ошибок (slog/zap), без паролей и токенов в логах.
- [ ] Стиль: gofmt/goimports, golangci-lint **с конфигом в репозитории**; нет магических строк; нет пакета `utils` (пакеты по смыслу); именованные DTO вместо анонимных `struct{}`; стандартная библиотека (`slices`, `maps`) вместо самописных хелперов; проверки на nil.
- [ ] Моки — отдельно от прод-кода (`mocks/`, mockery).
- [ ] `TODO` только со ссылкой на задачу.
- [ ] Бизнес-баги из разборов: перевод «самому себе», неатомарные изменения баланса — то есть **инварианты домена** проверены тестами.

## Тесты

- [ ] Тестируется **бизнес-логика** (переходы статусов, расчёты, ошибки и граничные условия), а не только «репозиторий вернул без ошибки»; табличные тесты.
- [ ] Слои: usecase — юнит-тесты с моками; repository и handler — интеграционные.
- [ ] Отдельная тестовая БД; e2e — в отдельном `docker-compose.e2e.yaml` со своими БД, переменными и сетью.
- [ ] Нет flaky: не завязываться на порядок map, текущее время без фиксации clock, общую БД между тестами.
- [ ] Тест проверен «поломкой»: временно меняешь ожидание — тест должен упасть.
- [ ] Покрытие проанализировано и описано в README (в старых разборах ошибкой считалось < 70%; кейс требует > 80%).

## Frontend (React + TypeScript)

- [ ] TypeScript; ESLint + Prettier настроены; импорты отсортированы и сгруппированы (`import/order`, `import/no-cycle`); `import type` отдельно.
- [ ] Архитектура выбрана и описана (README или `ARCHITECTURE.md`): `api/` (работа с сервером), `components/`, `pages/`, `types/`, `helpers/`; роутинг — в `App.tsx`.
- [ ] Работа с API вынесена в отдельный слой — компоненты не собирают URL и заголовки; адрес API — из переменной окружения.
- [ ] Токен и роль хранятся централизованно в одном месте; маршруты защищены по роли (и при ручном вводе URL).
- [ ] **На каждой странице с запросами — loading, error и empty**; ошибка предлагает действие (повторить, вернуться, написать в поддержку).
- [ ] Нет лишних запросов: двойной клик блокирован или debounce; нет последовательных запросов там, где можно параллельно; поиск — debounce, от 3 символов, частичное совпадение.
- [ ] Состояние: встроенные средства React, пока не нужно большее; фильтры синхронизированы с query-параметрами; после мутации данные обновляются.
- [ ] Валидация форм — zod; черновик формы — в localStorage (с троттлингом).
- [ ] Компоненты до ~150 строк; логика — в хуки, чистые функции — в утилиты; осмысленные имена (`TaskFormPopup`, `handleInputChange`); маппинг через `Record`, а не цепочки if; без `style={}` без необходимости.
- [ ] Error Boundary на страницах и формах (один переиспользуемый, с разными fallback, протестирован).
- [ ] UX: курсор-рука на интерактивных элементах, лоадеры, анимации появления, адаптивность (мобильный и десктоп), заглушка для картинки, раскрывашка для длинного текста, видимый скролл, кнопка «наверх» на длинных страницах.
- [ ] Нет лишних `console.log` (могут утечь приватные данные); dev-зависимости — в `devDependencies`.
- [ ] Комментарии к сложной логике объясняют «почему»; без тривиальных.
- [ ] Тесты: утилиты — граничные случаи; компоненты — рендер и взаимодействие; store — отдельно; зависимости (API, localStorage) замоканы.
- [ ] Большие списки (сотни элементов) — виртуализация; меньше 50 — не нужно.

## Эталон: задание Fullstack 2026 «каталог AI-ассистентов»

Ближайший аналог нашего кейса из заданий Авито (Go + PostgreSQL + React, мок LLM, роли). Что там требуют и проверяют — стоит повторить:

- `/dummyLogin` выдаёт тестовый JWT по роли с **фиксированным UUID** на роль, чтобы проверяющий воспроизводил сценарии.
- JWT содержит `user_id` и `role`; права проверяются централизованно (middleware); `user_id` берётся из токена, не из тела.
- **Запуск ассистента сохраняется всегда**: статус `pending` → `success` или `failed` (ошибка, таймаут, невалидный ответ провайдера), с текстом ошибки.
- **Мок LLM детерминированный**; реальный провайдер — за флагом/переменной, проект работает без ключа.
- **Системный промпт хранится и применяется на бэкенде**; фронт отправляет только пользовательский ввод и не получает системный промпт.
- README обязательно: схема БД и индексы; как обрабатывается запуск и сохраняется история; выбор стейт-менеджмента; **контракт мок-провайдера и пример итогового запроса в LLM**; обработка таймаута, невалидного ответа и ошибки провайдера; как переключиться на реальный API.
- Тесты: юнит на бизнес-сценарии; интеграционный/E2E на основной сценарий; негативные (неактивный ассистент, чужие права, ошибка LLM); минимум 3 фронтенд-теста.
- Плюсом: TypeScript, стриминг ответа, мобильная и десктопная версия, тёмная тема, Swagger, CI с покрытием, нагрузочный тест с результатами в README, конфиги линтеров, лайк/дизлайк ответа.
- В задании Backend осень 2026: **CJM пользователя кодом** (PlantUML или аналог, например Mermaid `journey`), **C4-диаграмма** уровня 2–3, схема БД, OpenAPI и миграции в репозитории, конфиг линтера; «будет плюсом приложить промпт или план, по которому писался проект».
