## Принципы разработки → как применить в прототипе

| Принцип Авито | В AI-buddy |
|---|---|
| Отвечаем за работоспособность своей системы; всегда знаем, что с ней происходит (дашборды, алерты) | `/healthz`, структурные логи (slog JSON), метрики запросов к LLM и инструментам; в README — какие алерты завели бы |
| Начинаем с проектирования, учитываем текущую архитектуру, не создаём сервис на каждую фичу | бадди — агент в существующей платформе, а не новая платформа; мок-сервисы имитируют существующие системы |
| Избегаем ненужной сложности; используем готовые инструменты | один Go-сервис + мок-MCP; без своего RAG-движка, если хватает простого поиска |
| Избегаем жёсткой связанности; не ходим в чужую БД или кэш; интеграция с событием, а не с сервисом | данные сотрудников и заявок — только через API/MCP сервиса-владельца |
| Внешний интерфейс важнее реализации; обратная совместимость (несовместимое — новой версией) | OpenAPI-контракт фронт↔бэк и контракты MCP фиксируются первыми |
| Документируем интерфейсы, особенности и нефункциональные требования | README + design.md + спеки |
| Не пишем бизнес-логику в БД | правила (сроки, права, статусы) — в Go-коде, в БД только целостность (NOT NULL, FK) |
| Шина данных — только для уведомлений о событиях, не для передачи состояния | события аналитики несут идентификаторы и тип, а не полный объект |
| Один источник правды; stateless-сервисы, ничего не храним на диске | история диалога и статусы — в Postgres/Redis, не в памяти процесса |
| Обратная совместимость миграций | миграции отдельными файлами, только добавляющие изменения |
| Асинхронность там, где можно; отказоустойчивость: сервис не ответил — деградируем, показываем заглушку, шлём метрику | MCP-сервис недоступен → бадди честно говорит, что действие сейчас не выполнить, и предлагает повторить/обратиться к наставнику |
| Запрашиваем только нужные данные | инструменты возвращают компактные ответы |
| Любое изменение легко тестируется автоматически; что не протестировано — не катим; Zero Bug Policy | TDD, покрытие > 80%, `make check` в CI |

## Шаблон Tech Design Review (TDR) — структура design.md и слайда архитектуры

Проблема (продуктовая или бизнесовая) → Описание решения → Схема зависимостей → **Компромиссы** (и техдолг: когда и как закроем) → **Альтернативы** → FAQ → Нагрузка (RPM, реплики, чтение/запись) → Ресурсы (похожие сервисы, конфигурация БД, хранилища, GPU) → Структура БД → **Информационная безопасность** (публичный API? персональные данные? модель угроз) → **Метрики** (бизнесовые, продуктовые, технические).

TDR обязателен, если решение затрагивает несколько юнитов, требует больше 3 человеко-месяцев, увеличивает техдолг или вводит новую технологию. AI-buddy подходит под все пункты — поэтому design.md в формате TDR выглядит «по-авитовски». Архитектурный комитет смотрит решения от 500 rps.

## Соседское соглашение (как команды правят чужой код)

Правило бойскаута; тесты — часть документации и должны падать при баге; ревью — не позже следующего дня; отклоняешь — аргументируй; кто сломал — тот чинит; владелец отвечает за тесты, метрики и логирование; при расширении функциональности покрытие не снижается («Keep Going Green»).

## Процессы и инструменты

- Scrum в продуктовых командах; release train — сайт дважды в день, микросервисы — continuous delivery; небольшие частые релизы.
- Структура: кросс-функциональные **юниты** (бэк, фронт, мобильные, QA, дизайн, продакт, аналитик), **кластеры** платформенные и продуктовые; Unit-Leader; TMG.
- **SPT** — обращения пользователей в Jira: Bug / Crash / Feature; приоритеты P0–P4 по матрице «частота × серьёзность» (всегда + crash/failure = P0); закрываем, только когда фикс в проде.
- **LSR** — разбор инцидентов, постмортем с фиксированными полями, action items с владельцем и сроком.
- **OKR** на уровне юнитов; Performance Review раз в полгода (апрель, октябрь) в инструменте «Перфоратор»; профили E1–E8 (стажёр — E1).
- Инструменты: Slack, Jira, Trello, Confluence, Tableau, Bitbucket, TeamCity, Miro, Google Docs. Из Backend-чек-листа: **PaaS** + консольная утилита **avito-cli** + PaaS-дашборд, **Grafana**, **Sentry**, **Observer**, **Redash**, Kubernetes через **Lens**, Bruno/Charles.
- **Avito PaaS** берёт на себя интеграцию с БД, логи и метрики, секреты, очереди, шину данных, live reload и запуск тестов — разработчик пишет бизнес-логику. Аргумент на защите: наш сервис — обычный Go-микросервис, его можно завести в PaaS.

## Ценности (пригодятся в презентации)

Всё начинается с потребностей пользователей; решай быстро и аргументированно; упрощай; вместе мы можем больше; главное — результат (цели в количественных метриках).
