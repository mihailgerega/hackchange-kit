## «Виталик» — это и есть «настройка ИИ-агентов с промптами и MCP» из кейса

- Пользователь видит только чат: веб (React/TS) или корпоративный мессенджер.
- Уровни: обычный чат → разовые артефакты (документы, ссылки) → **проекты** (контейнер знаний: базы знаний, инструменты, права доступа, совместная работа) → **агенты**. Агентом становится успешный проект, у которого есть **владелец, валидационные данные и инструменты**; у агентов единая маршрутизация.
- Слои: UI → backend (собирает сессию и настройки проекта в **контракт данных**) → оркестратор **PortalManager** (строит дерево агентов, выбирает модель на каждого, собирает контекст) + **ADK Runner** (ReAct-цикл: перед каждым вызовом модели — RAG-инъекция контекста; модель отвечает или вызывает tool / MCP / субагента) → слой инструментов (**RAG, внутренний поиск, gateway, MCP Hub**) → данные (MongoDB, Elasticsearch, PostgreSQL, S3).
- **MCP Hub**: инструменты подключаются с единым контрактом, владельцем, правами доступа и трассировкой; агент знает только контракт вызова, не детали системы.
- **RAG-конвейер**: загрузка (PDF, Excel, Confluence — синхронизация каждую ночь) → препроцессинг (таблицы, дедупликация) → индексация (чанки, эмбеддинги, Elasticsearch) → векторный и гибридный поиск с реранкером → сборка контекста с бюджетом токенов и цитатами → ответ. Модель вызывается только на последнем шаге.
- Ответ агента — **маршрут, ссылки, следующий шаг**. Типы вопросов: процессные («что надо сделать, чтобы…»), операционные («что указать в форме…»), маршрутизация («к кому идти…»).
- **Бенчмарки** агента: function calling (BFCL, ruBFCL, tau2), RAG и поиск, Tools/MCP (правильные аргументы, ошибки, задержки), доменный бенчмарк от владельца (эталонные ответы, LLM-as-a-judge, лайки/дизлайки). Оценивается поведение целиком: маршрут, вызовы, контекст, обоснованность.
- Доменные агенты уже есть: корпоративный центр, HR, аналитика и другие. AI-buddy естественно ложится в ветку HR/онбординга.

Рядом для разработчиков: **skills-hub** (магазин навыков с проверкой качества и безопасности), **mcp-hub** (доступ к внутренним MCP: код, документация, баг-трекер), **AVIDA** (автономный запуск агентов по расписанию или запросу), сервис **анонимизации данных**; для чувствительных данных используются **внутренние модели**.

## Правила проектирования MCP-инструментов (практики Авито)

- **Один инструмент — одна человеческая задача.** Не CRUD-обёртки над REST, а «подготовь заявку на отсутствие», «покажи мой план на неделю». Чем меньше вызовов до результата, тем надёжнее.
- **Мало инструментов**: параметр вместо нового инструмента, но не смешивать разные по смыслу действия. Группировать по серверам (сервис = сервер).
- **Распространённые имена** инструментов и параметров — модель угадывает их чаще.
- **Tolerant Reader**: принимать неидеальный ввод агента (дата в разных форматах — разобрать на сервере), а не падать.
- **Компактные ответы**: только нужные поля, экономия контекста. Запрашивать у сервисов только нужные данные.
- **Понятные ошибки**, из которых модель понимает, что делать дальше.
- Проверять сервер на **модели-середнячке**: она ошибается чаще и подсвечивает плохие описания.
- MCP — **защитный фасад** над микросервисами; лимиты, валидация аргументов, аудит и защита от prompt injection — в шлюзе (AI Gateway).

## Безопасность агента

- Косвенная prompt injection (атака ShadowLeak; доклад «Атаки на GenAI-агентов: OWASP на практике» — разбор агента поддержки от инъекции до XSS в админке и опасного вызова инструмента): текст из документов, заявок и ответов сервисов — **недоверенные данные**.
- Отсюда: запись — только после подтверждения человеком; права — в инструменте, а не в промпте; ответ модели рендерится без сырого HTML; контур GuardRails перед LLM — подозрительный ввод уходит человеку (так сделано в модерации); при низкой уверенности — к человеку.
- Персональные данные: синтетика в прототипе; в проде — анонимизация и внутренние модели.

## Агент или workflow

- Агент нужен, если шаги нельзя определить заранее, сценарии вариативны, данные и политики часто меняются.
- Иначе — детерминированный код. План адаптации, сроки чек-листа и напоминания — это код и крон, а не LLM. Это сильный аргумент на защите: LLM только там, где она даёт ценность.

## Промпты, оценка, качество

- **Промпт — параметр системы**: версии, история, эксперименты (в модерации для этого есть админка промптов, ею управляет менеджер).
- Как подать регламент модели: RAG (дешевле, но промахи поиска и отдельный контур с метриками), весь документ в контексте (просто, но дорого и падает внимание), компактный промпт по регламенту (дёшево и стабильно, сложнее поддерживать). Выбор надо обосновать в design.md. Для небольшой базы знаний прототипа годится «всё в контексте» с кэшированием стабильного префикса.
- **Эталонная выборка** размечается людьми и скрыта от агента; для неоднозначных вопросов допустимые варианты фиксируются **до** прогона (защита от подгонки); метрика учитывает частичное совпадение (micro F1), а не «всё или ничего».
- Раздел «**что система гарантирует, а что нет**» — честные границы.

## SDD и агентская разработка в Авито

- Руководитель тестирования Авито Авто называет **SpecKit, Superpowers и OpenSpec**; две рамки — спецификация и тесты (TDD); human-in-the-loop (ревью спеки, дизайна, тестов) и agent-in-the-loop (агент ревьюит агента); на каждый критерий приёмки — **ссылка на тест**; мутационное тестирование ловит «зелёные заглушки»; метрики DORA и контроль затрат на токены.
- Навыки: самодостаточные, проверяют предусловия, имеют evals (happy path и edge cases) и ревью доменного эксперта. «Вам не нужен навык», если нужен строго предсказуемый результат — тогда алгоритм в коде.
- Go для агентов: обвязка без фреймворка на `anthropic-sdk-go`; история сообщений передаётся в функцию и возвращается (stateless, можно продолжить на другом воркере); отмена через `context.Context` по всему дереву вызовов; вызовы инструментов одного хода можно выполнять параллельно; утечки горутин ловить профилем goroutine leak или `goleak`.
- В заданиях стажёров 2026: «Авито — AI-first компания», ИИ для кода рекомендуется, но за архитектуру отвечает автор; **плюс, если приложить промпт или план**, по которому писался проект.
