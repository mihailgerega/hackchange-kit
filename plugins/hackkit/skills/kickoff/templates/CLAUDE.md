# AI-buddy — Hack&Change 2026, кейс Авито

Прототип ИИ-наставника, который помогает стажёру освоиться в команде: отвечает на вопросы о процессах и инструментах с учётом контекста, показывает этапы адаптации и следующие шаги, выполняет действия через корпоративные сервисы (их имитации). Основной пользователь — стажёр; наставник, руководитель и HR BP участвуют в отдельных сценариях.

## Как мы работаем (плагин hackkit)

1. Новый сценарий или фича → `hackkit:grilling` (2–3 раунда вопросов) → `/opsx:propose <change-id>` по правилам `hackkit:spec-authoring`.
2. Утверждённый change → `hackkit:writing-plans` → `openspec/changes/<id>/plan.md`.
3. Реализация → `hackkit:subagent-driven-development` (или `hackkit:executing-plans`), всегда через `hackkit:test-driven-development`.
4. Перед словом «готово» → `hackkit:verification-before-completion` → `make check` → `/opsx:archive <id>`.
5. Перед сдачей → `hackkit:submission-check`, `hackkit:e2e-demo` (видео), `hackkit:pitch-deck`, прогон агента `hackkit:jury`.

Спецификации (OpenSpec) — источник правды для AI-функций и сдаются жюри. Код без сценария в спеке не пишем.

## Стек и структура

- `backend/` — Go {{GO_VERSION}}, `net/http`, PostgreSQL (pgx), Redis; MCP-серверы имитаций сервисов на `github.com/modelcontextprotocol/go-sdk`; LLM через интерфейс `agent.Model` (`hackkit:llm-agent-go`).
- `frontend/` — React + TypeScript + Vite, TanStack Query/Router, Zustand, Zod; тесты Vitest + Testing Library + MSW; e2e Playwright.
- `openspec/` — спецификации и изменения; `docs/` — архитектура, статус, демо-сценарий.
- Запуск: `docker compose up --build` или `make up` (без `.env`, всё со значениями по умолчанию), проверки: `make check`, покрытие: `make cover-check`, e2e: `make e2e`.

## Жёсткие ограничения кейса

- Только синтетические/обезличенные данные. Тестовые инструкции помечаем как тестовые и не выдаём за регламенты Авито.
- Права пользователя соблюдаются на сервере: недоступные сведения и операции не раскрываются и не выполняются. Роль берём из токена, не из аргументов модели.
- Сценарии с чувствительными ПДн и финансовыми операциями — вне области задачи.
- Покрытие строк кода команды тестами > 80% (цель 85%), отчёт воспроизводим: `make cover-check` → `coverage/REPORT.md`.
- Простые локальные операции UI < 1 с; запросы к LLM/сервисам не блокируют интерфейс: статус ожидания, таймаут, понятная ошибка, повтор.
- Внешний API: сервис, модель, переменная окружения и подключение ключа описаны в README; `.env.example` без секретов; `LLM_PROVIDER=fake` даёт детерминированный режим без ключа.
- Главный сценарий обязан проходить по README с чистого клона — иначе 0 баллов на допуске.

## Как оценивают (веса)

Онлайн-этап (40% итога): внедряемость и интеграции 30%, UX 25%, работоспособность сценариев 20%, техническая реализация 15%, безопасность и данные 5%, презентация 5%.
Финал (60%): ценность для стажёра и команды 20%, живая демонстрация 25%, обоснованность технических решений 20%, внедряемость и развитие 25%, защита 5%, командное владение 5%.
Отсюда приоритеты: сквозной рабочий сценарий → совместимость с платформой Авито (Go, PostgreSQL, Redis, авторизация и роли, MCP, ИИ-крон, feature flags, аналитика событий) → UX и демо → глубина.

## Как смотрят инженеры Авито

Жюри — инженеры Авито. Перед мержем и сдачей сверяемся с `hackkit:avito-context` (раздел `review-checklist.md`): запуск одной командой с дефолтами, слои handler → service → repository, интерфейсы на стороне потребителя, бизнес-правила в коде (не в БД), отдельные миграции, graceful shutdown, `errors.Is`, конфиги линтеров в репозитории, loading/error/empty на каждой странице, API-слой на фронте. Бадди позиционируем как доменного агента платформы «Виталик» с MCP-инструментами, а не как новую платформу. Тестовые инструкции помечаем как тестовые, на материалы Авито ссылаемся.

## Командная работа

- Владение файлами и статус — в `docs/STATUS.md`. Чужие файлы не правим, общий контракт `api/openapi.yaml` меняем только по договорённости (`hackkit:parallel-sessions`).
- Параллельные сессии — в отдельных git worktree. `main` всегда запускается через `make up`.
- Коммиты маленькие, сообщения в формате `feat|fix|test|docs(scope): …`.
